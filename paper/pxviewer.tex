\begin{abstract}
\pxviewer{} is an interactive application for inspecting, validating and
refining macromolecular models against experimental data. Atomic models are
read with the Computational Crystallography Toolbox (cctbx) into its
\emph{mmtbx} model framework, so every view, table and selection in the
application is derived from the same validated objects used by the Phenix
suite; structures are rendered by the Mol* toolkit, with Python and the
renderer connected by a live coordinate bridge that streams conformation
changes into the view without reloading topology. The desktop application
organizes inspection around the crystallographer's workflow rather than the
implementation's: residue, atom and geometry-restraint tables act as literal
selections that drive navigation, focus and clipping; MolProbity-style
validation is presented the same way, so a flagged residue is one click from
the camera. Interactive workflows built on the bridge include real-space
refinement into cryo-EM density, X-ray refinement judged against a live
mFo--DFc difference map, ligand fitting and restraint editing. Guided
tutorials walk new users through each of these tasks inside the running
program. \pxviewer{} is distributed as self-contained installers for macOS,
Windows and Linux that require no terminal or package manager.
\end{abstract}

\textbf{Keywords:} molecular graphics; model building; structure validation;
cryo-EM; crystallographic refinement; interactive refinement.

\section{Introduction}

Molecular graphics has occupied a special place in protein crystallography
since \emph{FRODO} \citep{frodo1978} and then \emph{O} \citep{o1991} showed
what interactive display could do for model building; the tradition continued
with \emph{Coot} \citep{coot2004, coot2010}, which remains the standard
interactive model-building tool for X-ray crystallography. Along a parallel
track, UCSF \emph{Chimera} and \emph{ChimeraX} \citep{chimera2004,
chimerax2018, chimerax2021} built the field's most capable general-purpose
visualization environment, and \emph{ISOLDE} \citep{isolde2018} demonstrated
that physically realistic interactive simulation could make low-resolution
remodelling both safer and faster.

Two changes have reshaped the technical landscape since these tools were
designed. First, the graphical interface of the PHENIX package
\citep{phenix2010, phenixgui2012} was a landmark in making sophisticated
crystallographic refinement accessible to non-experts. Behind it sits cctbx
\citep{cctbx2002}, whose \emph{mmtbx} model hierarchy, geometry-restraint
machinery and validation metrics encode decades of crystallographic
correctness. A viewer that reads models through cctbx would inherit all of
that. Yet the PHENIX GUI orchestrates workflows rather than visualising the
underlying objects: there is no viewer that natively presents cctbx model
hierarchies, restraints or validation results, and although PHENIX can launch
and drive Coot through an integration socket, Coot remains independent with respect to datatypes and data handling paradigms. 
In deciding how to implement a cctbx object viewer, we considered all available options.
One of the most competent molecular visualizers available runs not on the desktop but in the browser: Mol*
\citep{molstar2021} delivers publication-quality representations, per-atom
color theming and very large structures entirely in WebGL. Between them lies
a gap: cctbx owns the refinement competence but renders nothing interactively,
while Mol* renders superbly but is not yet used for refinement.

\pxviewer{} (Fig.~\ref{fig:gui}) bridges that gap. It keeps every crystallographic decision on the
Python side --- model I/O through cctbx's \texttt{DataManager}, geometry
restraints from cctbx's own proxies, MolProbity-derived validation, etc. It then
lets Mol* do visualization, what it does best. The two halves are joined by a live
coordinate bridge: a persistent channel over which Python streams the model
topology once, then conformation frames, selections, representations,
measurements and camera state as the model and the user's intent evolve.
The channel carries traffic in both directions: Python pushes conformation
frames while a minimization or ligand fit runs, so progress appears as molecular motion in the
renderer as it happens rather than at the end, and the renderer returns
picks, drags and iso-value changes to Python, so a running tool can respond
to the user mid-run.

A second design commitment shapes the interface. Tables of data are inherent to macromolecular tasks, researchers think in
\emph{tables of things} --- residues, atoms, restraints, validation flags, and in \emph{selections} of those things. 
In \pxviewer{} tables are a first class view into the underlying python objects. A table row \emph{is}
a selection: clicking a restraint row selects the atoms it restrains, and the
same selection machinery governs viewport picking, camera focus, clipping,
representations and filtering. Guided tutorials use the same state, so the
program can watch what the user does and acknowledge each step only when it
is truly done.

The result is intended to offer a complementary tool for users who already use the cctbx library in their work. 
Pxviewer provides a way to look at those objects graphically, analyze them, and even manipulate them with a user friendly point-and-click interface.

\section{Overview and architecture}

The application has four components (Fig.~\ref{fig:arch}).

\textbf{The data layer} is the \pxviewer{} Python package. Atomic models are
read by cctbx's \texttt{DataManager} into an \texttt{mmtbx.model.manager};
the viewer never parses structural data itself. Maps arrive through the same
path for CCP4, MRC and related formats, and reflection data through cctbx's
\emph{miller} arrays. Structures fetched by accession code from the Protein Data Bank
or EMDB take the identical path through cctbx, not through the available Mol* pathways. 
Enforcing this provides users a guarantee that whatever is seen in the viewer is a direct representation of 
the cctbx object.

\textbf{The live coordinate bridge} is a versioned WebSocket protocol. On
connect, Python sends the model topology once, as BinaryCIF; afterwards the
wire carries binary coordinate frames (one \texttt{float32} triple per atom),
a compact binary channel for per-atom attributes (e.g.\ B-factor or
local-resolution values used for coloring), and small JSON messages for
selections, representations, measurement primitives, non-covalent
interaction notation, clashes, camera state and background. Atom identity is
positional and fixed for a session: index $i$ on the wire is always atom
$i$ of the topology, which is what makes streamed conformation updates safe and fast.
This follows the convention of the underlying cctbx $i_seq$ atom property, and a provides a 
natural way to specify atoms between the Python model and Mol* view domains.
Table~\ref{tab:wire} gives representative messages.

\textbf{The renderer} is a Mol*-based frontend (TypeScript/React). It applies
each frame to the streamed topology in place, and representations update
coordinates rather than rebuild. The frontend reports viewport picks back over the
bridge. Representation state (type, coloring, opacity, scope) is specified in
Python via MolViewSpec and replayed to viewers that connect later.

\textbf{The desktop app} embeds the same frontend in QtWebEngine
(PySide6) beside a native controls window. Pyside is a natural fit for the Python-dominant cctbx ecosystem.
Users who prefer it can instead
point any browser at a session served by \texttt{pxviewer serve}.
The protocol is identical either way, and anticipates future development where the controls window could be implemented in an alternative to PySide6/Qt.
The separation is concrete rather than aspirational: all application state
and operations live in a GUI-agnostic \texttt{AppCore} that imports no widget
toolkit, and the desktop is an adapter over it --- \texttt{DesktopApp}
subclasses it to attach the windows. The same object runs with no display at
all, hosting the Mol* page in headless Chromium instead of QtWebEngine, which
is how agent-driven figure generation works on a machine with no GUI
(Sec.~\ref{sec:mcp}).
Enforcing a separation between the GUI widgets and the molecular view makes continued development as easy as possible.

The four components aim to map onto a model--view--controller pattern, with the
controller role split across two surfaces. The \emph{model} is the Python
session state owned by \texttt{AppCore}: the \texttt{mmtbx.model.manager}, the
current selection,
representation specifications, clipping and camera intent, etc. A single
authoritative store of everything the interface displays. The \emph{view} is
the Mol* frontend, which holds no  \pxviewer{} state of its own. It
renders the topology and frames it is given, and because it can be
reconstructed entirely from replayed state, additional or late-connecting
viewers attach transparently. The \emph{controller} role is shared between
the Qt controls window (which mutates model state in-process), and the
bridge's inbound channel, which turns viewport picks, drags and iso-value
changes into the same model mutations. Because the views and controllers are
interchangeable while the model is not, alternative front ends inherit every capability
without reimplementation.

\section{Inspecting models and data}

\subsection{Loading and viewing structures}

The \emph{Open} action accepts local model files (PDB, mmCIF and other
cctbx-supported formats), density maps and reflection files, or an accession
code to fetch from the PDB/EMDB. Several models can be loaded at once and
independently shown, hidden or made active in an objects list.
Often it is necessary for computation tasks to know which model and data (real space map or reflection file) 
should be paired together. Within cctbx for real space maps this is expressed as a \texttt{map\_model\_manager} object.
When opening files, \pxviewer{} automatically pairs map and data if both files are selected together. In the case
where model and data are not opened together, the object list offers a user the option to 
pair a map and data manually. Within the \pxviewer{} data model, a model and data paired this way would create the 
appropriate underlying cctbx python object (a \texttt{map\_model\_manager} object). 

\subsection{Representation}

Below the object list is a Representation pane. Representations follow
MolViewSpec's vocabulary: cartoon/ribbon, ball-and-stick, spacefill,
surface, carbohydrate. Coloring can be done by element, chain, secondary
structure, residue properties, arbitrary uniform colors, or any per-atom
attribute (B-factor, occupancy, or values supplied or computed by the user). Clipping is available across slab, sphere and
selection-driven modes.  Non-covalent
interaction notation (hydrogen bonds, salt bridges, hydrophobic and other
contact kinds) can be supplied explicitly from Python or inferred by Mol*.

\subsection{Tables and selections}

The Geometry tab presents the model as a list of tables: \emph{Components} lists residue groups (residues, ligands, waters);
\emph{Atoms} is a table of per-atom attributes that remains
responsive past $10^5$ atoms; and one table per restraint type
lists bonds, angles, dihedrals, chiralities and planarities, read directly
from the cctbx restraint proxies. Every row is a literal selection of the
atoms it describes, and selections are shared state across the whole
application. A row selected in a table highlights those atoms in the
viewport, a group of rows selected in a table highlists the inclusive set of shared atoms. An atom picked in the viewport selects its atom row. Camera focus and
the clip sphere can be bound to the running selection, and keyboard stepping
walks the table one row at a time. Pick granularity is
explicit: atom-level by default, promoted to residue where the displayed
representation offers no atom-sized target (such as cartoon/ribbon), and is visible and
overridable in the Selection pane. Also in the Selection pane, the user can enter arbitrary cctbx string selections.
Internally, selections from any source are converted to cctbx integer selections, which are then passed along the wire to the viewer.
Operating on strict integer selections ensures that the viewer always has a consistent and efficient way to reference atoms, 
and removes the ambiguity surface inherent to string-based selection translation.

\subsection{Restraint editing}
Restraint edits --- custom bonds, angles or
metal-coordination restraints the monomer library cannot know --- are
authored from the atoms themselves inside the GUI and can be shared as a
PHIL file for use in Phenix refinement, so an interactive session produces
artifacts that survive it.

\section{Validation}

The \emph{Validation} tab runs the MolProbity-derived checks available through
cctbx: rotamer outliers, Ramachandran outliers, CaBLAM backbone outliers,
C$\beta$ deviations, cis- and twisted-peptide flags. Each produces a
table of flagged residues and deposits the corresponding MolProbity markup in
the viewport (Fig.~\ref{fig:validation}). Tables behave exactly like the
geometry tables: a row is a selection of the atoms involved, and table rows
are selections, so the path from ``this residue
is an outlier'' to ``show me'' is one click.

\subsection{Hotspots}
Two further tools consolidate the picture. \emph{Hotspots} aggregates the
per-residue checks into a single per-atom severity field mapped onto the
structure, because a region worth rebuilding usually trips several checks
at once and a picture finds such regions faster than five tables.

\subsection{Real space map-model aggreement}

A deposited cryo-EM resolution is a global average; \pxviewer{} computes
local resolution and colors the structure or map by it, making the
soft-periphery/sharp-core distinction directly visible.

\section{Interactive workflows}

Several interactive workflows are provided to demonstrate the capabilities of the bridge. 
We are careful not to use the term "refinement" because nothing provided in \pxviewer{} is
a sufficient replacement for a full refinement workflow. The best use of \pxviewer{} is as one
component of an interative refinement workflow that includes a dedicated refinement engine. What
\pxviewer{} can provide, is better referred to as "density guided minimization". It aims to provide
the user with a tangible way to explore the relationship between the model and the density, as well as
a proof of concept for how to integrate core cctbx functionality into an interactive viewer.

\subsection{Real-space refinement into cryo-EM density}

Real-space refinement \citep{rsr2018} minimizes the model against the
density map itself. In \pxviewer{} the cctbx machinery runs on the Python
side while the bridge streams each accepted conformation into the viewport,
so the user watches the fit converge in the map rather than waiting for a
final structure. Restraints, weighting and secondary-structure constraints
are the same ones the Phenix suite applies.

\subsection{X-ray refinement with a live difference map}

X-ray refinement is judged against data. \pxviewer{} computes the
mFo--DFc difference map from the loaded reflections as the model changes and
streams it live: positive and negative contours update around the region
being rebuilt, so the map functions as real-time feedback rather than a
post-hoc verdict. The precedent is established, Coot has long updated
maps dynamically during model building, and ISOLDE made continuous feedback
during interactive refinement an organizing principle
\citep{coot2004,coot2010,isolde2018}. \pxviewer{} compresses the same
working loop into the interactive session, driven by recomputation of the
crystallographic difference map using cctbx computational primitives rather than by interactive
dynamics.

\subsection{Ligand fitting}

The ligand-fitting workflow locates unmodeled difference density and fits a
flexible ligand into it.

\section{Guided tutorials}

Foundational tasks, including every workflow above is also a guided tutorial, built into the application's
\emph{Tutorials} menu. A tutorial is a non-modal ``coach'' that loads its
own example data (so its instructions always describe the structure actually
on screen), then steps the user through the task one instruction at a time.
Two properties distinguish it from documentation: each step carries a
predicate over live application state, so the step is acknowledged only when
the user has genuinely done the thing; and a \emph{Show me where} button
flashes the exact widget the step refers to. The tutorials double as
regression tests --- the same step sequences run headlessly in the test
suite --- so they cannot drift out of sync with the interface.

\section{Scripting and reproducibility}

The same bridge that drives the GUI is a public API. A
\texttt{LiveSession} can be created from a model file, an existing
\emph{mmtbx} manager or synthetic coordinates; it exposes selections (by
index, by the Phenix atom-selection language, or by mask), representations,
per-atom coloring, measurements, interaction notation, clashes, camera
state and mouse selection reported back to Python. The desktop app embeds an
IPython console bound to the active model's session, so the GUI and scripts
drive the same object.

Views are reproducible: \emph{Save view} serializes the session --- loaded
objects, representations, colors, clipping, selections, visibility,
background and camera --- to a JSON file that restores the scene exactly.
Two storage modes are offered. \emph{Bundled} (the default) writes every
object's coordinates and maps beside the view file, so the figure reproduces
anywhere and survives edits made since the data was loaded; data that cannot
be reconstructed from an external file, such as a computed map or modified
coordinates, is always bundled. \emph{Referenced} views instead point at the
files objects were loaded from, keeping a suite of figures that share one
dataset lightweight. This is intended to make published figures
reproducible artifacts rather than screenshots of a state no one can
reconstruct. MolViewSpec \citep{mvs2025, mvstoolkit2024} pursues the
complementary approach: a declarative, viewer-neutral scene specification
authored as data and rendered by any conforming viewer; a saved view
instead records the state of a running application, including state that
exists only in that session.

\section{Interactive scripting}
\label{sec:scripting}

For work whose shape cannot be anticipated --- a one-off geometric check, a
scripted color scheme, a figure staged just so --- the \emph{Console} tab
embeds a full IPython kernel inside the application. Rather than reflect a
subset of the API through bespoke widgets, the console puts the real objects
in front of the user: the kernel runs in-process, so names in its namespace
\emph{are} the objects the application holds. Evaluating
\texttt{session.highlight(...)} in the console drives the live viewport
directly, and state created there is visible to every panel --- the GUI and
scripts manipulate one scene, not two views of it.

Table~\ref{tab:console} lists what is bound at startup and the underlying
cctbx objects one expression away. \texttt{session} rebinds automatically
when the active model changes, so a script written against it always acts on
the model the user is looking at. Because the underlying objects are cctbx's
own --- the \emph{mmtbx} model, its \texttt{map\_model\_manager}, miller
arrays --- console work composes with the same machinery the panels use
rather than a parallel scripting dialect. Bare \texttt{help} prints this
same list in the console itself, and \texttt{help(obj)} is still Python's.

The kernel is a real Jupyter kernel on the standard wire protocol, not a
private in-process loop, so the Console tab is only its most convenient
frontend. It writes a connection file at startup, and any Jupyter client
can attach to the same namespace --- \texttt{jupyter console --existing
\emph{file}} for a terminal session, a notebook for cell-based work. Code
executed through any of these frontends runs in the application's process
against the same live objects; names assigned in one client are visible in
the others. This is also what an agent executes against
(Sec.~\ref{sec:mcp}). The console is optional: it requires
\texttt{qtconsole} and \texttt{ipykernel} (the \texttt{console} extra), and
the tab shows an install hint when they are absent.

This arrangement inverts the usual relationship between a Jupyter kernel
and a molecular viewer. Existing integrations embed the viewer inside the
notebook: \emph{py3Dmol} \citep{py3dmol2015} renders a static 3Dmol.js
scene into the cell output --- deliberately one-directional, so notebooks
remain valid without a kernel --- while \emph{NGLview}
\citep{nglview2018} couples an NGL widget to the kernel over ipywidget
traitlets and, since release 4.0, offers a Mol* backend as well. Mol*
itself reaches notebooks as the \texttt{ipymolstar} anywidget
\citep{ipymolstar}, the trajectory-oriented \texttt{MolSysViewer} widget
\citep{molsysviewer}, a static HTML rendering of a MolViewSpec state via
\texttt{molstar\_notebook} \citep{mvs2025}, and the py3Dmol-compatible
\texttt{molview} package \citep{molview}. All of these put the viewer
inside the notebook, owned by its kernel and by the cell that created it.
\pxviewer{} runs the other direction: the kernel belongs to the
application, and the notebook is a client of it. There is no widget in
the cell to go stale; a terminal session, a notebook and an MCP agent
observe and drive the same running scene, and closing the client leaves
the viewer --- and the state it displays --- intact.

\section{Agentic control through MCP}
\label{sec:mcp}

\pxviewer{} exposes a Model Context Protocol (MCP) server, so an external
agent --- a language-model client, a pipeline script or another program ---
can drive the \emph{visible} viewer rather than a headless approximation of
it. The server attaches to a running application over HTTP for interactive
sessions, or spawns its own instance over stdio; in both cases the user
watches the same window the agent is manipulating, which makes an automated
figure-construction sequence inspectable and interruptible. Where no display
exists at all, the spawned instance is the GUI-agnostic core: the Mol* page
runs in headless Chromium, so frames, screenshots and saved views are the
same rendered output the desktop would produce --- \texttt{python -m
pxviewer mcp} works unchanged on a figure-generation box, with no X11 or Qt
widgets involved.

Rather than mirror the API through a schema of wrapped verbs, the server
hands the agent the application's own Python kernel: one tool,
\texttt{python(code)}, executes in the same namespace the Console tab
shows (Sec.~\ref{sec:scripting} describes the bindings;
Table~\ref{tab:console} lists them). The objects are the API --- \texttt{session.model} is the
real \emph{mmtbx} model, selections made by executed code \emph{are} the
application's selections, and names assigned in one call persist for the
next, so an agent can stage intermediate cctbx objects in the namespace
rather than re-deriving them. Discovery is the namespace's own: the agent
reads \texttt{api} and \texttt{help}, inspects \texttt{dir(session)}, and
composes verbs the same way a user at the console would. What remains as
named tools is what execution cannot do as well --- viewport liveness,
page recovery, and binary image output (Table~\ref{tab:mcp}).

The cost of that choice is real, and it is deliberate. A schema of named
verbs is also a capability boundary --- a host can grant or deny each
operation --- and \texttt{python(code)} collapses that to a single
permission: execute code in the application's process. This is the
code-execution pattern Anthropic's own MCP guidance recommends for
composable APIs, on the reasoning that an agent composes more faithfully
through real objects than through a large catalogue of thin wrappers; it
suits a viewer whose value is exactly the breadth a live cctbx model
exposes, provided the trust envelope is drawn correctly.

\centering
\caption{The MCP surface: one execution tool, plus operational plumbing
that exec cannot do as well. Everything the console can express is
reachable through \texttt{python}.}
\label{tab:mcp}
\begin{tabular}{@{}lp{10.5cm}@{}}
\toprule
Tool & Purpose \\
\midrule
\texttt{python(code)} & execute in the app's IPython kernel --- the same
namespace as the Console tab; returns
\texttt{\{status, stdout, stderr, result, data, error\}}, with
\texttt{data} the cell's mimebundle \\

\bottomrule
\end{tabular}
\end{table}

Two properties are treated as contract rather than convention. First,
\emph{actions report postconditions, not requests}: exec'd code returns
the real exception with its traceback, so a failed call cannot masquerade
as success; \texttt{save\_screenshot} returns only after the bytes are on
disk; and every background job --- fetch, validation, map computation ---
records its outcome where \texttt{status} can read it. Second, \emph{the
state is shared, not mirrored}: an agent reading
\texttt{session.model.get\_sites\_cart()} holds the same array the panels
are showing, and a selection it makes is simultaneously the selection the
tables highlight --- there is no agent-only representation to keep in
sync. The trust envelope is therefore drawn tightly: the endpoint listens
on loopback only and refuses requests carrying a browser \texttt{Origin}
header, so it gives an agent the same trust a console user already has
without becoming a network surface.

Recovery is likewise agent-visible. Because every viewport message queues
behind serialized scene work, a single slow state-tree update makes a
healthy page look dead; \texttt{ping} bypasses that chain and reports which
update is holding it and for how long, distinguishing ``busy'' from
``wedged''. When the page is genuinely dead, \texttt{reload\_viewport}
rebuilds it --- Python-side state survives and is replayed on reconnect,
since the model is authoritative and the view holds no state of its own. A
regression test pins the tool list exactly, so a renamed or missing tool
fails the suite rather than silently breaking agents that learned the
surface.

\section{Distribution and availability}

\pxviewer{} is distributed as self-contained installers for macOS
(Apple~Silicon), Windows~10/11 (x86\_64) and Linux (x86\_64), downloadable
from the project releases page. Each packages a complete conda environment
--- Python, cctbx, the chem\_data monomer and validation libraries, Qt and
the built Mol* frontend --- so installation needs neither a terminal nor a
package manager, and the Linux bundle works fully offline. A source
install (a single script that bootstraps conda, builds the environment and
the frontend) supports development on macOS and Linux, and a
\texttt{noarch} conda package is available for managed deployments.

\pxviewer{} is source-available software (see the license accompanying the
distribution); source code, issue tracking and releases are at
\url{https://github.com/cschlick/pxviewer}.

\section{Implementation notes}

\textbf{Atom identity.} Frames, selections and per-atom attributes are
positional throughout: atom $i$ is row $i$ of the topology. The atom set may
not change mid-session, which turns the streaming problem into a fixed-size
contract rather than a reconciliation problem.

\textbf{Packaging.} The conda recipe is the single source of dependency
truth; platform build scripts pack a fresh environment into the artifact
(dmg, NSIS archive-in-installer, tar.xz), build the validation caches inside
it, and trim the chem\_data datasets the application cannot reach (BLAST
databases for eLBOW, the standalone secondary-structure regularization
library). Prefix fixup is deferred to launch/install time so the bundles are
relocatable.

\textbf{Testing.} A headless suite covers the Python layer and GUI
invariants; visual passes run the renderer on all three platforms, including
the tutorial step sequences --- the walkthroughs ship only if they still
work.

\section{Discussion and outlook}

\pxviewer{} deliberately occupies the space its predecessors left between
them. From Coot it takes the premise that crystallographic primitives ---
restraints, monomer chemistry, validation --- should drive the interface;
from ChimeraX it takes the standard for rendering quality, onboarding and
distribution; from ISOLDE it takes the conviction that refinement should be
visible and interruptible. Its distinguishing choices are the ones those
tools could not have made at their inception: cctbx as the sole authority
for crystallographic meaning, a browser-grade renderer as the sole
authority for pixels, and a persistent bidirectional bridge in between.

Natural directions follow from that architecture: multiple simultaneous
viewers on one session, collaboration on shared selections and views,
deeper integration of the live bridge with Phenix refinement programs, and
extension of the tutorial framework into user-authorable walkthroughs for
teaching.
